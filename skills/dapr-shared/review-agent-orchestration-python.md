# Agent Orchestration Checklist — Python

Apply each rule below to every file in `agent_files` + `component_files` when `topology == orchestrator`. When `topology == single-agent`, the review skill applies none of these rules (see `review-agent-orchestration/SKILL.md` step 2); the only rule that can fire then is `DAG-ORCH-010`, and only when `topology_unverified == true`.

Rule source: see [`../create-agent-python/REFERENCE.md`](../create-agent-python/REFERENCE.md) — sections "Multi-agent orchestration (native `dapr-agents`)" and "Wrapper `main.py` — the shape".

## Code shapes and flavors

Python multi-agent projects come in three flavors (`flavor` from `review-detect-target-agent.md`): `native` (the files import `dapr_agents`), `wrapper` (the files import `diagrid.agent.`), and `mixed` (both, typically a native coordinator with wrapper specialists). Flavor is decided per file by its imports, not by dependency lines (wrapper projects depend on `dapr-agents` too). In a `mixed` project, apply each rule's detection to each entrypoint/file according to **that file's** flavor. The rule id and its meaning are the same for every flavor.

Markers: a wrapper agent is a `DaprWorkflow\w*Runner(` call; a native agent is `DurableAgent(` in a file that imports `dapr_agents` (`diagrid.agent.strands` ships its own `DurableAgent`, which is a wrapper).

| Concern | `native` (`dapr-agents`) | `wrapper` (`diagrid[<extra>]`) |
| --- | --- | --- |
| Inbound topic | `AgentPubSubConfig(agent_topic=...)` on `DurableAgent(pubsub=...)`; an explicit config without `agent_topic=` uses the agent `name`. When `pubsub=` is omitted and a component named exactly `agent-pubsub` exists, it is auto-wired as `agent_topic="<name>.topic"` (name lowercased, spaces → `-`) and `broadcast_topic="agents.broadcast"` | `runner.serve(pubsub_name=..., subscribe_topic=...)` — both arguments are required |
| Outbound / team topic | `AgentPubSubConfig(broadcast_topic=...)` — coordinators (agents with `orchestration_mode` set) broadcast their final result to it | `runner.serve(pubsub_name=..., publish_topic=...)` publishes the run result after the workflow completes |
| Coordinator → specialist dispatch | Child workflow on the specialist's app id (`appid` + `metadata.workflow_name` from the agent registry) — no per-specialist topic. The specialist can be a native agent or a wrapper runner (`mixed`) | No built-in dispatch: wrappers never look agents up. A wrapper coordinator hands work off over pub/sub (`publish_topic=`, or `DaprClient().publish_event(...)` in a tool); `<domain>.requests` / `<domain>.results` is only a suggested naming |
| Loop bound | `DurableAgent(execution=AgentExecutionConfig(max_iterations=...))` (default `10`) | `max_iterations=` on `DaprWorkflowAgentRunner`; `max_steps=` on `DaprWorkflowGraphRunner`, `DaprWorkflowDeepAgentRunner`, `DaprWorkflowHolmesRunner`. Defaults in `DAG-ORCH-002` |
| Registry | `registry=AgentRegistryConfig(...)`, or auto-wired from a component named exactly `agent-registry` (team `default`) when `registry=` is omitted. Required by coordinators | `registry_config=` (a dapr-agents `AgentRegistryConfig`) on the runner, or auto-registration into a component named exactly `agent-registry` (team `default`). Wrappers only register themselves; `DaprWorkflowHolmesRunner` never registers |

## Rule-id map (Python vs .NET)

Rule ids are stable once published. Gaps in the id range mean the rule is implemented only on one side.

| Rule id      | Python | .NET | Notes                                                                 |
| ------------ | :----: | :--: | --------------------------------------------------------------------- |
| DAG-ORCH-001 |   ✓    |      | Python-specific — an agent's inbound topic collides with a topic it publishes to. |
| DAG-ORCH-002 |   ✓    |  ✓   | Loop bound (`max_iterations` / `max_steps` / `MaxIterations`).       |
| DAG-ORCH-003 |   ✓    |  ✓   | Topic naming convention. Python: info, accepts `<name>.topic`, `agents.broadcast` and `<domain>.(requests\|results)`. .NET: see its file. |
| DAG-ORCH-004 |   ✓    |  ✓   | Coordinator references specialists not declared in `dapr.yaml`.      |
| DAG-ORCH-005 |   ✓    |  ✓   | Agent registry missing.                                              |
| DAG-ORCH-006 |   ✓    |      | Python-specific — module-level shared state across agents.           |
| DAG-ORCH-007 |   ✓    |  ✓   | Duplicate `appID`/port in `dapr.yaml`.                               |
| DAG-ORCH-008 |   —    |      | Retired (see below); id reserved, do not reuse.                      |
| DAG-ORCH-009 |   ✓    |  ✓   | Redis component uses empty `redisPassword:` outside localhost.       |
| DAG-ORCH-010 |   ✓    |      | Python-specific — wrapper project classified single-agent with several entrypoints (`topology_unverified`). |
| DAG-ORCH-011 |   ✓    |      | Python-specific — wrapper topic arguments without `pubsub_name=`.    |
| DAG-ORCH-012 |   ✓    |      | Python-specific — wrapper pub/sub subscriber runs the agent inside the delivery. |
| DAG-ORCH-013 |   ✓    |      | Python-specific — two runners of the same wrapper framework in one process. |
| DAG-ORCH-014 |   ✓    |      | Python-specific — `mixed` team: wrapper specialist not registered for the native coordinator. |

New .NET rules should reuse shared ids where semantics match; reserve Python-only ids and do not reassign them.

**DAG-ORCH-008 — retired** (coordinator without memory configuration). Its premise, "the coordinator loses context between runs", is false for `dapr-agents` 1.0.9: native memory is keyed per workflow instance (`<name>:_memory_<instance>`), so no `memory=` setting carries context across runs, and an explicit `memory=` is replaced by state-store memory whenever `state=` is set or an `agent-workflow` component is auto-wired. The in-run case is not orchestration-specific and is covered by the `review-agent-memory` rules. Never emit this id.

| Rule id      | Severity | What to detect                                                                                                                          | Why it matters                                                                                  | Suggested fix                                                                                |
| ------------ | -------- | --------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| DAG-ORCH-001 | critical | An agent's effective inbound topic equals a topic it publishes to. **native:** the effective `agent_topic` equals the effective `broadcast_topic` (see the defaults in the table above). **wrapper:** `runner.serve(...)` with `pubsub_name=` whose `publish_topic` equals its `subscribe_topic` | Creates a pub/sub loop: the agent re-triggers itself (a native coordinator's own final broadcast lands on its direct-message topic and starts a new run; a wrapper subscriber receives its own published result as a new task). | Keep the inbound topic distinct: `agent_topic="<name>.topic"` with `broadcast_topic="agents.broadcast"` (native), or different `subscribe_topic` / `publish_topic` values such as `<domain>.requests` in, `<domain>.results` out (wrapper). |
| DAG-ORCH-002 | warning  | The tool-call loop bound is not set explicitly. **native:** `DurableAgent(...)` without `execution=AgentExecutionConfig(...)`, or with an `AgentExecutionConfig(...)` that has no `max_iterations=`. **wrapper:** `DaprWorkflowAgentRunner(...)` without `max_iterations=`, or `DaprWorkflowGraphRunner` / `DaprWorkflowDeepAgentRunner` / `DaprWorkflowHolmesRunner` without `max_steps=`. Do not flag `diagrid.agent.strands.DurableAgent(...)`: its bound is fixed at 10 and has no parameter | The run falls back to a default that differs per framework and is invisible in review: native `10`; openai_agents, claude_agents, langchain, pydantic_ai `25`; adk `100`; langgraph and deepagents `max_steps` `100`; holmesgpt `max_steps` `10`; crewai the agent's `max_iter` (25 unless set); strands `25`; smolagents the agent's `max_steps`. A coordinator usually needs a different bound than its specialists. | Pass `execution=AgentExecutionConfig(max_iterations=<N>)` (native) or `max_iterations=<N>` / `max_steps=<N>` (wrapper); typical: 10–20. |
| DAG-ORCH-003 | info     | A topic name matches none of: `<name>.topic` (the agent or app name, the native auto-wired form), `agents.broadcast`, `<domain>.requests`, `<domain>.results`. **native:** explicit `agent_topic=` / `broadcast_topic=` in `AgentPubSubConfig(...)`. **wrapper:** `subscribe_topic=` / `publish_topic=` in `runner.serve(...)`. **Both:** `topic_name=` in explicit `publish_event(...)` calls | Consistent names make the team's message flow readable and match what `dapr-agents` auto-wires (`<name>.topic`, `agents.broadcast`). No runtime behavior depends on the name. | Use `<name>.topic` for an agent's inbound topic and `agents.broadcast` for team broadcasts (native), or `<domain>.requests` / `<domain>.results` for wrapper pub/sub. |
| DAG-ORCH-004 | warning  | Coordinator publishes to a topic whose `<domain>` prefix does not match any declared specialist `appID` in `dapr.yaml`. **wrapper:** the coordinator's `publish_topic=`. **Both flavors:** explicit publish calls (`DaprClient().publish_event(topic_name=...)`). Native registry-based dispatch has no per-specialist topic, so a native coordinator without explicit publish calls has nothing to check | Coordinator sends work to a non-existent specialist; messages are dropped.                       | Ensure every targeted `<domain>` has a corresponding specialist app in `dapr.yaml`.           |
| DAG-ORCH-005 | critical (native coordinator) / info (native, no coordinator) | No agent registry for a native agent: `component_files` has no component named `agent-registry` **and** no native agent file passes `registry=AgentRegistryConfig(`. Severity is **critical** when a native `DurableAgent` sets `orchestration_mode=` (it is a coordinator); **info** when the project has native agents but no coordinator. **wrapper-only projects:** not checked — wrappers never look agents up, so no registry is needed (a wrapper specialist in a `mixed` team is `DAG-ORCH-014`) | A native coordinator looks up its team in the registry and fails with `RuntimeError: registry_state must be provided to use agent registry`. Native agents without a coordinator only need a registry if a coordinator should dispatch to them later. | Add `resources/agent-registry.yaml` with `keyPrefix: none` (see `dapr-shared/agent-statestore-registry.md`); the native agent auto-wires it, or pass `registry=AgentRegistryConfig(...)` explicitly. |
| DAG-ORCH-006 | warning  | A specialist agent imports module-level state shared with the coordinator via the filesystem / SQLite                                    | Cross-agent shared in-process state breaks durability and scaling guarantees.                    | Communicate only via pub/sub, registry dispatch, or a Dapr state store.                       |
| DAG-ORCH-007 | warning  | `dapr.yaml` has two apps with the same `appID`, `appPort`, `daprHTTPPort`, or `daprGRPCPort`                                              | Port collisions prevent one or both sidecars from starting; invisible in the logs until timeout.| Assign each app a unique port per dimension.                                                  |
| DAG-ORCH-009 | warning  | `agent-pubsub.yaml` / `agent-registry.yaml` / `agent-memory.yaml` / `agent-workflow.yaml` has `redisPassword: ""` AND the project references Redis endpoints other than `localhost` / `127.0.0.1` | Unauthenticated Redis outside localhost; any reachable process can publish to topics or read/write state. | Set `redisPassword` via `secretKeyRef`; configure Redis AUTH / ACLs; or pin `redisHost` to a loopback address in dev.|
| DAG-ORCH-010 | info     | `topology_unverified == true`: a `wrapper` project has more than one agent entrypoint but no pub/sub marker, so it was classified `single-agent` | The agents may still work together without Dapr pub/sub: LangGraph subgraphs, deepagents `AsyncSubAgent` sub-agents called over the Agent Protocol (HTTP), or a native coordinator dispatching to them through the agent registry. A false single-agent classification silently skips every other rule here. | Confirm the project is single-agent. If the entrypoints are separate agents that talk to each other, wire them over `agent-pubsub` (`pubsub_name=` + `subscribe_topic=` / `publish_topic=` on `serve()`) or behind a native coordinator, and re-run this review. |
| DAG-ORCH-011 | critical | **wrapper:** `runner.serve(...)` passes `subscribe_topic=` or `publish_topic=` without `pubsub_name=`; or `DaprWorkflowHolmesRunner(...).serve(...)` passes any pub/sub argument | `serve()` subscribes and publishes only when `pubsub_name` is set too, and never falls back to the discovered `agent-pubsub` component; `DaprWorkflowHolmesRunner.serve()` ignores pub/sub arguments entirely. The agent silently never receives or publishes messages. | Add `pubsub_name="agent-pubsub"` to the `serve(...)` call (or expose the Holmes runner over HTTP only). |
| DAG-ORCH-012 | Please verify | **wrapper:** `runner.serve(...)` with `pubsub_name=` and `subscribe_topic=`. Report once per project, citing the first such call and naming the others | The subscription handler runs the whole agent inside the delivery request and acks only when the run ends. Each delivery starts a new workflow instance (`<prefix>-<session_id>-<random>`), so `session_id` / `thread_id` do not deduplicate: a broker redelivery (for example after a timeout on a long run) starts a duplicate run. The result is published outside the workflow, after it completes, and a publish failure is only logged. | Confirm duplicate runs on redelivery are acceptable and the broker's delivery timeout exceeds a typical run; otherwise make downstream consumers idempotent or start runs over `POST /agent/run`. |
| DAG-ORCH-013 | warning  | **wrapper:** two or more `DaprWorkflow\w*Runner(` calls imported from the same `diagrid.agent.<framework>` module are constructed in one process (the same file or import chain, on the same execution path) | Each framework keeps its tool registry, default workflow-input factory and (LangGraph) node registry at module level; a second runner clears or overwrites them, so the first agent calls the wrong tools or fails. | Run one runner per framework per process: give each agent its own app in `dapr.yaml`, or select the agent with a command-line argument as the `diagrid` examples do. |
| DAG-ORCH-014 | Please verify | **mixed:** a native coordinator (`DurableAgent` with `orchestration_mode=`) and wrapper specialists, where a wrapper specialist's app has no component named exactly `agent-registry` in its resources path and its runner passes no `registry_config=`; or the specialist is a `DaprWorkflowHolmesRunner` (never registers) | The coordinator finds specialists only through the registry (team `default` when auto-wired). A wrapper that does not register is invisible to it. `keyPrefix: none` on the shared registry component is inferred, and native-to-wrapper dispatch has not been verified end to end. | Load the same `agent-registry` component (with `keyPrefix: none`) in every specialist app, keep the team names equal, and confirm the coordinator lists and reaches each specialist. |

## Confidence notes

- DAG-ORCH-001 — Compare the effective values, not only the literal arguments: an explicit native `AgentPubSubConfig(...)` without `agent_topic=` uses the agent `name`, and without `broadcast_topic=` has no broadcast topic; an omitted `pubsub=` with an `agent-pubsub` component auto-wires `<name>.topic` / `agents.broadcast`, which never collide.
- DAG-ORCH-003 — Do not report the SDK defaults (the agent `name` used when `agent_topic=` is omitted, or the auto-wired `<name>.topic`). If the project uses a different naming scheme consistently, report it once rather than per topic.
- DAG-ORCH-004 — Requires reading both the coordinator file and `dapr.yaml`. A `publish_event(...)` inside a tool runs in an at-least-once workflow activity, so a retry publishes the task again and the specialist runs twice; mention `DAG-TOOL-001` (`review-agent-tools`) in the Why when the publish is inside a tool.
- DAG-ORCH-005 — In a `mixed` project, decide by the native coordinator's file; the wrapper specialists are covered by `DAG-ORCH-014`.
- DAG-ORCH-010 — Always reported under "Please verify", never under a graded severity section. Cite the `dapr.yaml` (or the first entrypoint) as the location. Mention `AsyncSubAgent(` or a native `orchestration_mode=` if the scan sees one.
- DAG-ORCH-012 / DAG-ORCH-014 — Always reported under "Please verify": the behavior depends on the broker's redelivery settings (012) and on registry wiring that is not yet verified end to end (014).
- DAG-ORCH-013 — The `diagrid` examples build several runners in one file but construct only the one selected by `sys.argv`; do not flag runners on separate branches.
