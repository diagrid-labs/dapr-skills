# Agent Observability Checklist — Python

Apply these rules to every Python agent project: native `dapr-agents`, `diagrid` framework wrappers, and `mixed` projects. The **Applies to** column says which flavor a rule targets. Decide the flavor **per agent file by its imports** (`dapr_agents` → native, `diagrid.agent.` → wrapper), not by the dependency line: in a `mixed` project (for example a native coordinator with wrapper specialists) apply each native or wrapper rule to the files of that flavor only. Rules marked `all` that read `dapr.yaml`, `resources/` or `README.md` are evaluated once per project; `DAG-OBS-003` and `DAG-OBS-005` are evaluated per file.

Rule source: see [`../create-agent-python/REFERENCE.md`](../create-agent-python/REFERENCE.md) — section "Observability".

**What the runtimes provide.**

- **Sidecar (both flavors)** — workflow and activity spans come from the Dapr sidecar when `dapr.yaml` points at a tracing `Configuration` (`configFilePath:`).
- **Native `dapr-agents`** — `DurableAgent(agent_observability=AgentObservabilityConfig(...))` (import from `dapr_agents.agents.configs`) adds agent, LLM and tool spans and an OTel `LoggingHandler`. The config is resolved once, in the constructor, from three tiers: the `agent_runtime` key of an `agent-runtime` state component (lowest), then `AgentObservabilityConfig.from_env()`, then the explicit `agent_observability=` (highest). It is **off by default**: nothing is exported unless `enabled` and `tracing_enabled` (or `logging_enabled`) resolve to `True`, and the exporter defaults to `console`. The environment equivalents are `OTEL_SDK_DISABLED=false`, `OTEL_TRACING_ENABLED=true`, `OTEL_LOGGING_ENABLED=true`, `OTEL_TRACES_EXPORTER` / `OTEL_LOGS_EXPORTER` (`otlp_grpc`, `otlp_http`, `zipkin` for traces, `console`; any other value, including the standard `otlp`, falls back to `console`), `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_HEADERS`, and `OTEL_SERVICE_NAME` (default: the agent name, lower-cased, spaces replaced by `-`). When enabled, the `httpx` and gRPC clients are instrumented.
- **`diagrid` wrappers** — built-in OpenTelemetry, set up **only inside `runner.serve()`**. It is a no-op until an OTLP endpoint is configured through `OTEL_EXPORTER_OTLP_ENDPOINT` (or the `agent-runtime` state component); `OTEL_SDK_DISABLED=true` turns it off. The exporter is **OTLP gRPC only** (insecure channel; `OTEL_EXPORTER_OTLP_PROTOCOL` is not read). Most runners install a global tracer provider whose `service.name` is `OTEL_SERVICE_NAME` or else the runner class name, and attach an OTel `LoggingHandler` to the root logger; the CrewAI runner instead patches CrewAI's own tracer provider and the Strands runner adds the exporter to Strands' tracer provider. Every runner instruments the gRPC client only (not `httpx`, `requests` or `aiohttp`). diagrid's Strands `DurableAgent` (`diagrid.agent.strands.DurableAgent`) has no `serve()` and sets up no telemetry.

Where to look for environment variables: `env:` blocks in `dapr.yaml` (per app or under `common:`), `.env` files the app loads, `os.environ[...]` assignments in agent files, and deployment manifests inside the scope.

## Confidence notes

- DAG-OBS-001 — Opt-out is allowed. If `dapr.yaml` contains an explicit comment like `# observability: off`, the README documents an external observability vendor, or the project runs on Catalyst (managed tracing), downgrade to `info`. App-level export (DAG-OBS-014 satisfied for native files, or an OTLP endpoint with `serve()` for wrappers) only partially satisfies this rule: keep it as a warning, and say in the finding that app spans exist but sidecar spans do not.
- DAG-OBS-005 — Heuristic; requires grepping for `httpx.` / `requests.` / `aiohttp.` calls inside tool bodies and checking whether `headers=` includes `traceparent` or `inject(`. Default to "Please verify" when unsure.
- DAG-OBS-011, DAG-OBS-014, DAG-OBS-018 — When an `agent-runtime` state component exists in `resources/`, the configuration may live in that store and cannot be read statically: report under Please verify instead of the listed severity. For a wrapper using the Pydantic AI runner, the store is ignored (only the environment is read), so do not downgrade DAG-OBS-011 for it.
- DAG-OBS-011 — For the CrewAI runner it is not verified that the patched CrewAI tracer produces spans when no global tracer provider is installed. When a CrewAI wrapper app does set an endpoint, report DAG-OBS-011 under Please verify ("endpoint set; confirm CrewAI spans reach the collector") instead of reporting nothing.
- DAG-OBS-012 — Only the app environment counts. A sidecar `tracing.yaml` with `endpointAddress: "localhost:4318"` and `protocol: http` is correct and is not a finding.
- DAG-OBS-013 — Always reported under Please verify: whether analytics is acceptable is a policy question the code cannot answer. Do not report it when no such deployment constraint is documented.
- DAG-OBS-015 — A custom FastAPI / CLI entrypoint that calls `run_async` is a legitimate choice; the finding is about the missing telemetry, not the entrypoint shape.
